# CastVault

**从「生成角色」到「经营角色资产」。** 不是又一个生成单图的 AI 绘画工具，而是让 AI 角色成为可复用、可保持一致性的资产库。

> 演示项目：数据为本地演示数据，页面所有指标均标注「演示口径」，非生产实测。

---

## 为什么做这个

目标用户是 OC 创作者、网文与漫剧作者。他们的痛点不在「生成」——生成能力早已过剩——而在生成之后：

1. **跨场景一致性难**：同一角色换个角度、换个场景就「换脸」，撑不起连载式创作；
2. **角色无法沉淀**：每次从零开始，设定散在聊天记录和草稿里，不能复用、不能版本化迭代。

## 三个关键产品决策

### 决策一：从「生成」转向「资产」

- **决策**：核心不是生成，而是角色的复用与一致性管理。
- **备选**：做又一个 AI 绘画 / 角色生成工具。
- **判据**：生成是红海且底层模型能力趋同；「同一角色跨场景保持一致」是连载创作者的真痛点，且它需要产品化设计（字段、版本、复用），不是单纯堆模型能力。

### 决策二：一致性双轨——LoRA + IP-Adapter

- **决策**：同时提供 LoRA 专属训练（单角色约 15 分钟，重资产、高一致）与 IP-Adapter 注入（轻量快速、无需训练）两条路径。
- **备选**：只押注其中一种。
- **判据**：不同创作阶段对「快」与「准」的需求不同——试稿用 IP-Adapter 快速验证方向，角色定型后用 LoRA 锁定一致性；单一路径必然牺牲其中一端。

### 决策三：保留手动编辑权

- **决策**：AI 生成人设档案后，用户可以手动再编辑，AI 不锁定最终结果。
- **备选**：全自动生成到底，减少操作步骤。
- **判据**：创作类产品中用户对「失控」的容忍度极低；角色是创作者的情感投射，最终定义权必须在人手里。

## 功能与信息架构

| 路由 | 页面 | 做什么 |
| --- | --- | --- |
| `/` | 首页 | 产品定位、能力概览、入口 |
| `/generate` | 生成 | 立绘 + 人设档案 + 声线设定三件套，整体入库 |
| `/gallery` | 角色资产库 | 按 name / role / style / episodes / reuse / version 管理角色，支持导入与删除、版本迭代 |
| `/consistency` | 一致性验证 | LoRA 与 IP-Adapter 双轨对比、多角度对齐、盲评结果 |
| `/about` | 关于 | 产品说明与设计主张 |

## 明确不做什么

- 不做通用绘画工具——只服务「角色资产」这一场景；
- 不做视频生成；
- 不承诺「绝对一致」——一致性数据为双人盲评的自评口径，样本量小，仅作方向性验证。

## 指标与口径

| 指标 | 数值 | 口径 |
| --- | --- | --- |
| 一致性双人盲评 | 10 场景 × 2 轮，18/20 判为同一角色 | 演示口径（自评） |
| LoRA 单角色训练时长 | 15 分钟 | 演示口径 |
| Prompt 成功率 | 40% → 90% | 演示口径 |

Prompt 成功率提升靠三件事：结构化分层描述 → 风格约束 → 负面提示词 + 模板库。

## 交互主张

**AI 负责起草，人保留手动编辑与最终定稿权。** 生成结果不是终稿，是可编辑的草稿。

## 技术栈

React 18 + Vite 6 + react-router-dom 7 + Tailwind CSS + GSAP。

## 本地运行

```bash
npm install
npm run dev      # 开发
npm run build    # 产物输出到 dist/
npm run preview  # 本地预览构建产物
```
